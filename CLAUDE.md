# hoi3-reversing: the fact base

*These rules are for `hoi3-reversing/`. Opened from the `workspaces/hoi3` root, all four of these
files arrive at once - apply each to its own folder.*

This is **what is known about `hoi3_tfh.exe`** - the static reverse engineering of one 32-bit
MSVC build of Hearts of Iron 3: Their Finest Hour. Nothing here launches the game and nothing
here is compiled. A claim is checked by **reading the bytes**.

It was a subfolder of the BiceLib DLL project until **2026-10-07**, four levels inside the
BlackICE mod's repository. It is its own repository now because it has two consumers rather
than one, and burying it in either would have made the other a second-class reader of its own
research. The 62 commits that ever touched it were replayed onto this repository, so `git log`
and `git blame` on a findings file still date a claim.

## Two consumers, two layers, and which one sets the bar

| | **BiceLib** | **OpenHOI3** |
| --- | --- | --- |
| what it is | the C++ module that loads into the running game | a rewrite in the spirit of the original, on its own technology |
| what it reads here | **offsets and addresses**, plus the prose | **the prose**, and nothing else |
| why | it has to find a field in a live process | it has to know what the original *computes* |
| if a fact here is wrong | a running game crashes | a design reference misleads |

So **BiceLib sets the accuracy bar**, because it is the only consumer that *executes* against
these facts. A wrong offset in the record reaches a live process through a `GameClasses`
constant; the same error reaching the rewrite costs a paragraph. Both layers stay, as peers:
addresses are build-specific and belong to the DLL, mechanics are build-independent and belong
to both.

**The dependency rule, which is what keeps the repositories separable:**

    this repository    depends on nothing
    BiceLib            depends on this one - offsets and prose both
    OpenHOI3           depends on this one - PROSE ONLY, never a build-specific offset
    OpenHOI3           never depends on BiceLib

The last line is the one worth stating, because the tempting shortcut - "the DLL already worked
this out, read its header" - imports build-specific offsets into a project whose whole premise
is its own technology.

**The seam with BiceLib:** a fact found here becomes code by being written **twice** - once into
`ghidra/project.json`, so the record and Ghidra agree, and once into a
`BiceLib/GameClasses/*.hpp` constant, so the DLL can use it. The headers cite the findings file
that established each offset. Keep doing that: it is the only link between a magic number and
the evidence for it.

## Where the other repositories are

`python scripts/roots.py` prints it. Five roots, each found by a **marker** rather than by
counting `..` levels, because counting is exactly what a move breaks and it breaks it silently -
the join still yields a path, just the wrong one.

| root | marker | who needs it |
| --- | --- | --- |
| `REVERSING` | `ghidra/project.json` | this repository |
| `BICE` | `BiceLib.sln` | the record cites `GameClasses` headers |
| `MOD` | `history/countries` + `.git` | `scripts/dupekeys.py`, `scripts/definesMap.py` read the mod's data |
| `GAME` | `hoi3_tfh.exe` + `tfh` + `common` + `history` | `scripts/image.py` and friends read the executable |
| `OPENHOI3` | `project.godot` | `scripts/checkrefs.py` checks the findings citations written there |

`$HOI3_<NAME>` overrides any of them, then `roots.json` (git-ignored; `roots.example.json` is
the template), then discovery. **A marker has to describe the real thing, not merely appear in
it** - `GAME` asks for four, because `hoi3_tfh.exe` alone first answered a folder holding one
large-address-aware copy of the executable and nothing else.

Do not reintroduce a hardcoded path or a counted `..` to reach another repository. Both existed
here until 2026-10-07 and two of them had already been wrong for a day.

The write-ups are in `findings/`, the toolkit in `scripts/`, the live probes in `probes/`, and
the parallel-agent staging area in `fragments/` - `incoming/` and `merged/`, which hold JSON
fragments and not prose. **Commands are run from this folder**: `python scripts/progress.py`,
`python ghidra/buildFindings.py`. Every script finds its own data through `scripts/roots.py`, so
none of them care what the current directory is - but the documented command lines all assume
the repository root.

**After moving anything, run `python scripts/checkrefs.py`.** It checks every reference that
claims to be a path - in the findings prose, the other documents, the `GameClasses` headers and
the mod's own `docs/` - and exits 1 if one does not resolve. A reference that cites a document
or script by bare name is deliberately left alone and not checked; `README.md`'s layout table is
what resolves those.

It earns its keep at exactly these moments. It grew two blind spots' worth on 2026-10-05, after
a reference to a deleted header survived a full clean pass: it now also reads **`.json`**, which
means `ghidra/project.json` - a third of the fact base, and its comments cite paths constantly -
and its pattern matches **`BiceLib/...`** as well as this tree's own folders, because a
reference pointing *outward* is as load-bearing as one pointing in. Together those took it from
391 references to 627. On the split itself it caught four more, in the mod's own documents,
pointing at where this repository used to live.

**A reference carrying this repository's old name is still correct.** 106 of them begin with
the `reversing/` prefix as of 2026-10-07, most in `GameClasses` headers citing the evidence for an offset, and
`checkrefs.py` maps that prefix to wherever `roots.py` found this tree. So the prefix is the
*logical* name of the fact base, the repository can be renamed again without touching the prose,
and there was never any need to rewrite the most load-bearing references in either half.

`bicelib_findings.json` is skipped by name because it is generated from `project.json`, so a
breakage there is a copy of one already reported - and fixing the generated copy would be fixing
the wrong file.

**`python scripts/checkindex.py` is the other half of the same idea.** `checkrefs.py` asks
whether every reference that was written down resolves; this asks whether anything is missing
from a list, which no reference check can answer - an absent reference is exactly what there
is nothing to check. It compares `findings/` against the index at the end of `CANDIDATES.md`,
which is how anyone finds the evidence for a claim. On 2026-10-07 that index was 6 files
behind with a count 18 out, because a write-up is finished when it reaches `findings/` and
the index is a separate hand edit afterwards. **A write-up is not finished until the index
lists it.**

## Before reading a function, ask whether it is already known

One command, before the work and not after it:

    grep -n 0x1BFC10 ghidra/project.json
    python -c "import io,json; print([e['name'] for e in json.load(io.open('ghidra/project.json',encoding='utf-8'))['addresses'] if int(e['rva'],16)==0x1BFC10])"

An address can already be recorded under a name you would not have guessed, with an extent and
a caller list better than the ones you are about to derive - and the record's prose is a third
place to look, because a function is sometimes *named inside another entry's comment* without
having an entry of its own. All three have happened, in both directions, within one session:
`CUnit::SetLeader` was sitting in `CLeader::null`'s comment and got recorded off that, and then
`RegisterCommandTypes` was duplicated as `RegisterPersistentPrototypes` because this grep was
not run - the existing entry had the real extent, which the new reading had failed to find.

So: **check the rva, check the name, and grep the comments.** `buildFindings.py` prints a `!!`
line for two entries on one rva, but it is the backstop and not the check - by the time it fires
the work has been done twice.

## Whatever is read goes into `project.json`, every time

**The maintainer's standing instruction, 2026-10-07: always add reversed things to
`project.json`.** A function read, a field identified, a constant pinned down - it is entered
in the record in the same session, whoever wanted it and whichever consumer it was for. A
findings file on its own is not a finished reading: prose is where the reasoning lives, and
the record is what Ghidra, the DLL's headers and the next reader are built from.

It was said because of exactly that shortcut. A session working on the rewrite needed four
functions read for a mechanics spec, read them, wrote `findings/FINDINGS-distribute.md`, and
stopped there, reporting the record as "yours to decide". It is not a decision. The rewrite
only ever takes the prose, which is what makes it tempting to leave the rest undone when the
rewrite is what asked.

So, each time:

1. one fragment in `fragments/incoming/`, named for its topic - `fragments/README.md` has the
   shape, and every address entry needs a signature (or `no_signature`), a confidence and
   `evidence`;
2. `python ghidra/mergeFindings.py --check`, then without `--check`. Only that script writes
   `project.json`;
3. `python ghidra/buildFindings.py`, `python scripts/checkSignatures.py`,
   `python scripts/progress.py`, and the headless apply against a copy, below;
4. the findings file listed in `CANDIDATES.md`, and `checkindex.py` and `checkrefs.py` run.

A register-convention signature must place **every** parameter - `out@stack:4` beside
`country@EDI` - or `checkSignatures.py` lists it as having parameters with nowhere to live.

## The pipeline, in order, and it is idempotent

1. edit `ghidra/project.json`
2. `python ghidra/buildFindings.py`
3. apply with `analyzeHeadless.bat ... -postScript ApplyBiceLibFindings.java overwrite`
   - **the full command, with the install path and which project, is in `ghidra/README.md`.**
     Ghidra lives under `Documents\Ghidra\`, deeper than a shallow `find` will reach, and the
     current project is `Hoi3_v12.1.2`, which since 2026-10-07 opens only with the
     **12.1.4** install. Run against a **copy** - the maintainer's is usually
     open and holds the lock.

**`failed: 0` and `struct fields: 0` on a second run is the pass mark**, and as of 2026-10-05 it
is actually reachable. It was not before: the apply ran in a period-2 cycle over six field
declarations on five structs - four consecutive passes gave `6, 5, 6, 5` fields - because each
phase wrote one side of a by-value sub-object and cleared the other. Two causes, both fixed: the
four `flags_persistent` fields were re-declaring at the parent level what Ghidra already models
inside `CFlags` and are deleted, and `CLeaderHistory` was 0x44 in Ghidra against the record's
0x24, so **a declared `size` is now authoritative downward as well as upward**. Three passes
after the fix: `7, 0, 0` fields and no conflicts.

So a non-zero second run means something real. `ghidra/README.md` has the whole account, and
`ghidra/PrintStructs.java` prints what Ghidra actually holds for a structure, which is the first
thing to run when a field will not settle. Read the `!` lines for a failure, which
`grep -F '!'` over the headless output will show.

**This said `failed: 2` until 2026-10-04, and the two it excused were explained wrongly.** The
claim was that Ghidra had given `CSimpleRandom::GetInteger` (`0xAA2B10`) and `GuiTypeTree_Find`
(`0xA7DEE0`) bodies running past their real ends, swallowing `MT19937Next` (`0xAA2B90`) and
`TernarySearchTreeFind` (`0xA7E030`). Both predecessors are in fact **thunks that tail-jump into
the function below them**, and Ghidra's small bodies for them are correct:

    0xAA2B10  mov eax, ecx            0xA7DEE0  push ebp; mov ebp, esp
    0xAA2B12  jmp 0xAA2B90                      cmp [ecx+4], 0; lea eax,[ecx+4]; jne
    0xAA2B17  int3 ...                          xor eax,eax; pop ebp; ret 4
                                      0xA7DEF3  pop ebp; jmp 0xA7E030
                                      0xA7DEF8  int3 ...

So there was never an over-long body to arbitrate; Ghidra had **merged each thunk with its
tail-call target into one function**, which is ordinary behaviour on a tail call and not a wrong
end. And the byte-level argument the old text offered - "`0xA7DEE0` ends `ret 0xc` at
`0xA7E028`, then five `int3`" - was about a **different function**: `functionStart(0xA7E020)`
answers `0xA7DF60`. Two functions were conflated, and the conclusion that the record's names
were right happened to be true for an unrelated reason. In the current project all four are
proper function entries. If the pair ever comes back, repair the **thunk**, not the target.

## Conventions that are invisible in the bytes

**Addresses in `project.json` are rvas** against an image base of `0x400000`, as are the
`GameClasses` offsets ("module relative" is the same thing). Disassemblers print virtual
addresses. This is trap 1 and it is still the most frequent error.

**Numbers are thousandths** - `237964731` is `237964.731`. And the savegame is plain text, which
makes it the cheapest oracle available for any scale question.

**Mark inference as inference.** The vocabulary is `confirmed` / `likely` / `inferred`. The
maintainer's standing request is to be able to see where a fact came from, so a claim resting on
a scale rather than an instruction says so, and a negative result says what search produced it -
see the closing section of `TRAPS.md` on why a negative needs a positive control.

**A derived timestamp is not a fact.** `progress.py` read the census date off the file's mtime,
which worked only while the file had never been copied; the first clone set it to the moment of
checkout and published a census date that was really the age of the checkout. `ghidra/census.json`
records `taken` now. Anything dated should carry its date, not have one inferred from the disk.

## If you delegate reversing work to subagents

Their `Write` is refused for `findings/FINDINGS-*.md`, so they hand the file back as prose in
their report and **someone has to transcribe it**. Do that in the same session; once the context
is compacted the only copy is in the session transcript, and getting it back out is a scripted
job over a 600 MB file. Give every agent `TRAPS.md` - that is what it is for.

**Every brief must demand the same two things at the top of the report, before any prose.** Added
2026-10-05, after wave 13 came back in four different shapes - one agent opened with a table of
what it landed, one with a fragment summary, two buried it - which meant finding "what actually
changed in the record" was four different searches. These go in every brief, verbatim:

> **Open your report with a synopsis of 2-5 sentences** - what you set out to settle, what you
> settled, and anything you *corrected* rather than added. No preamble before it.
>
> **Then a table of every function your fragment touches**, one row each, before the write-up:
>
> | rva | name | new or revised | confidence | one line |
>
> Use `revised` for anything that already had a record, and say in the last column what changed
> about it. If the fragment touches no function, say so in one line rather than omitting the table.

They are the two things that get read first and relayed to the maintainer, so they are the
agent's job and not the collecting session's. The synopsis is what the maintainer reads; the
table is the index to the record, and it is what makes a cross-agent collision or an unexpected
`revised` visible at a glance instead of after a full read. **A `revised` row is the one that
needs checking** - an agent adding a name costs little if it is wrong, and an agent overwriting
one costs a published claim, so verify those off the bytes yourself before merging.

**And a second table, on the same terms, for `struct_fields`** - also verbatim in every brief:

> **Then the same table for every struct field your fragment touches:**
>
> | struct | offset | name | type | new or revised |
>
> Same rule: `revised` for anything that already had a record, and say what changed - a name, a
> type, or both. If the fragment touches no field, say so in one line.

**This was "ask for it when the brief is field-heavy" for about an hour, and that was wrong.**
Wave 13's brief A had no field framing at all, its function table read **`0 revised`** -
seventeen clean additions - and its two most consequential results were *field* overwrites:
`CCountry +0x604` `base_ic` -> `TotalIC` and `+0xF34`/`+0xF38`
`has_faction`/`faction_leader_tag` -> `isSubject`/`Overlord`, nine revisions among 76 field
records. A function-only table would have presented that agent as pure addition and hidden
exactly the work that most needed checking.

Two things follow. **Which briefs are field-heavy is not knowable when the brief is written** -
A's wasn't, and the one that looked field-heavy on paper landed five fields and revised none.
And **a field overwrite is as expensive as a function overwrite**: a wrong type is what reaches
the decompilation, which is how `CDiplomacyStatus +0x14` ended up showing `void*` while the
record also held `CAlliance*`. So both tables are unconditional, and the `revised` rows of both
are what you verify off the bytes before merging.

Note a field record has no `confidence` of its own - `FIELD_KEYS` is `offset`, `name`, `type`,
`comment`, `source` - which is why that column is in the function table and not this one.

## reagent

`GitHub/reagent` is a third-party tool (Ghidra plus LLMs, reconstructing C/C++ functions behind
build and parity gates). It is **not** part of this pipeline and nothing here depends on it.
Four things if it is used:

- **It is not installed.** No `re_agent` module, no `re-agent` or `ghidra-bridge` on PATH.
- **Drive it from a scratch project, against a copy of the Ghidra project.** The maintainer's
  holds the lock, as with the apply.
- **Its output quality is a function of how named the project is.** This record applies 3058
  addresses, 317 structs and the nested vftable slots idempotently; pointed at a named project
  it reads real code, pointed at a fresh import it reads `FUN_004...`.
- **It costs model calls.** Set a budget before the first run.

It generates C/C++ and gates on a build of the target tree, so it cannot gate anything against
a C# rewrite that is deliberately not behaviour-identical. Its honest use here is studying the
algorithmically dense functions, not producing the rewrite.

## Always

- **Never commit unless asked.**
- Scripts go in the scratchpad, written with the `Write` tool. Bash heredocs here mangle
  apostrophes and collapse `\x00`-style escapes into real bytes; both have corrupted a file, and
  one of them corrupted a `\Users` path during the split itself.
- **Only valid for this build of `hoi3_tfh.exe`.** Every offset, address and vftable index is
  build-specific.
